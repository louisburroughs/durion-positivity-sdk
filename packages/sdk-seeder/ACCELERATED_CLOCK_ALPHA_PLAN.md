## Accelerated Clock Alpha EC2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> `superpowers:subagent-driven-development` (recommended) or
> `superpowers:executing-plans` to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run `sdk-seeder` against the existing alpha Durion backend with a
synchronized accelerated clock that starts one year in the past and converges on
the present day, producing a year of realistic operating history in the normal
alpha environment.

**Architecture:** `pos-events` remains the owner of the Spring application
`Clock`. A Compose override supplies identical clock anchors to every backend
JVM and adds a one-shot `sdk-seeder` container. The accelerated clock is a
*converging* clock: virtual time starts one year before deployment, advances at
the configured scale, and stops accelerating the moment it reaches wall time.
After convergence every JVM reports ordinary system time, so the alpha stack is
left in a normal-clock state and no separate environment, temporary Compose
project, or stack swap is required.

**Tech Stack:** Java 25, Spring Boot 4, Spring Cloud Gateway, Maven, Docker
Compose, Amazon ECR, Amazon EC2, AWS Systems Manager, GitHub Actions,
TypeScript, Node.js

---

### Why a Separate Environment Is Not Required

Earlier drafts assumed an isolated accelerated Compose project because a
year-scale scenario would write timestamps far ahead of wall time. That risk
came from anchoring virtual time at or after the present. It disappears when the
clock is anchored one year in the past:

- Virtual time is always less than or equal to wall time, so the run never
  writes future-dated records, future expiries, or future audit history.
- The clock converges to wall time by construction and then ticks at scale 1,
  so no restoration step is needed to return alpha to a normal clock.
- Seeded data lands on real historical dates, which is exactly the year of
  operating history alpha is meant to demonstrate.

The run therefore uses:

- The normal alpha Compose project, host, ECR registry, and SSM control plane.
- The persistent alpha PostgreSQL, Kafka, and named volumes.
- A single alpha redeploy that adds the accelerated profile, followed by a
  one-shot seeder run in the same network.
- No teardown of alpha data and no maintenance window for a stack swap.

The one remaining constraint is ordinary deploy hygiene: the accelerated profile
changes application behavior for the duration of the catch-up window, so
announce the run and avoid concurrent alpha deploys while it is in progress.

### Target Clock Contract

Every accelerated backend JVM receives the same values. `virtual-start` is
`real-start` minus one year and both are generated once, immediately before
deployment:

```properties
spring.profiles.include=accelerated
pos.time.accelerated.scale=1000
pos.time.accelerated.zone=UTC
pos.time.accelerated.real-start=2026-08-20T12:00:00Z
pos.time.accelerated.virtual-start=2025-08-20T12:00:00Z
pos.time.accelerated.converge=true
```

Virtual time is defined as:

```text
virtual(t) = min(virtualStart + scale * (now - realStart), now)
```

The clock closes a one-year gap `G` in `G / (scale - 1)` real time, because wall
time advances during catch-up:

| scale  | real time to reach the present |
| ------ | ------------------------------ |
| 1,000  | about 8 h 46 m                 |
| 8,760  | about 1 h 0 m                  |
| 26,280 | about 20 m                     |

Pick the scale from the run budget and the slowest poller that must observe
every virtual boundary. Once `virtual(t)` reaches `now`, the clock returns wall
time for the rest of the process lifetime.

The gateway exposes this read-only response under the accelerated profile:

```json
{
  "virtualTime": "2025-11-03T08:30:00Z",
  "scale": 1000.0,
  "zone": "UTC",
  "accelerated": true,
  "converged": false,
  "realStart": "2026-08-20T12:00:00Z",
  "virtualStart": "2025-08-20T12:00:00Z"
}
```

The seeder runs inside the Compose network with:

```properties
SEEDER_BASE_URL=http://pos-api-gateway:8080
SEEDER_SECURITY_SERVICE_URL=http://pos-security-service:8080
```

No new public EC2 ingress is required.

- [x] **Step 6a: Extend enforcement to SQL written as strings**

The bytecode rules above are Java-only. They cannot see `now()` inside a
`@Query` string, which is exactly how the `pos-supplier` lease writes in Step 4
escaped review. Add a companion check covering SQL text.

Read the annotation values through ArchUnit for the `@Query` case:

```java
methods().that().areAnnotatedWith(Query.class)
    .should(notWriteDatabaseTime())  // reject now(), current_timestamp,
                                     // clock_timestamp, localtimestamp,
                                     // current_date in the SET clause
```

Match case-insensitively and only on write statements. `INSERT ... VALUES` and
`UPDATE ... SET` fail; a `WHERE` comparison passes, because read-side filters
against database time are covered by Step 8.

ArchUnit reads annotation values but not arbitrary string literals, so pair it
with a source-scanning test in `pos-archunit` that walks every `src/main/java`
file and applies the same pattern to string literals. That second test also
catches `entityManager.createNativeQuery(...)` and SQL assembled from
concatenated constants, which the bytecode rules miss entirely.

Both checks need an explicit allowlist keyed by fully-qualified method name,
each entry carrying a one-line justification. Seed it with the
`SupplierScheduleLeaseRepository` lease-acquisition and heartbeat statements,
whose `leased_until` and `last_heartbeat_at` values are deliberately real-time.
An empty or comment-free allowlist entry fails the test.

Neither check covers Flyway migration files. Those are reviewed against the
Step 8 list and verified by the Step 9 query.
